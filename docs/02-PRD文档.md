## 1. 产品概述

### 1.1 一句话定位

> **云原生时代的 Spark 替代品**：Rust 自研内核带来原生性能与低资源成本，Go 控制面带来简单的集群运维体验，对象存储优先的存算分离架构天然贴合云上部署。

### 1.2 愿景

让任何规模的数据团队都能用得起、管得动大数据计算引擎：

- **更快**：向量化执行 + 零拷贝列式内核，批处理吞吐对标或超过 Spark；
- **更省**：无 JVM 内存开销，同等作业资源成本降至 Spark 的一半量级；
- **更易**：单静态二进制部署、自研轻量集群、SQL 即接口，运维门槛从"大数据工程师"降到"后端工程师"。

### 1.3 价值主张（按角色）

| 角色 | Spark 现状痛点 | Flux 提供的价值 | 可量化承诺 |
| --- | --- | --- | --- |
| 平台负责人 | 资源成本高、JVM 调优玄学 | 资源利用率翻倍量级提升，参数面收敛 | NFR-PERF-3：内存峰值 ≤ Spark 50% |
| 运维 / SRE | 部署链路重、排障要读 JVM 日志 | 静态二进制 + 原生 metrics/tracing + doctor 巡检 | 部署从"小时级"到"分钟级"；1 条命令巡检 |
| 数据分析师 | 小查询延迟高、交互体验差 | 常驻进程 + 低启动开销 | NFR-PERF-5：热启动 ≤ 500ms |
| 数据开发 | 流/批两套系统、语义不一致 | 长期统一的批流 SQL 语义 | M5 起同一引擎同一 SQL |
| 应用开发者 | 嵌入 Spark 需 JVM 进程链 | Rust SDK 单机嵌入式 | 进程内零外部依赖 |

### 1.4 产品形态与边界

形态：单机嵌入式模式（M1）、自研 Master/Worker 集群（M2）、K8s Operator（M7+）。非目标（不做）：BI 可视化产品、Notebook 产品、自研存储引擎/索引服务、通用资源调度市场、Spark 私有 API（RDD）级兼容。

## 2. 市场与竞品分析

### 2.1 行业趋势

1. **降本增效成为主旋律**：数据平台算力支出中，Spark 类引擎的 JVM 开销（对象头/装箱/GC 预留）与超额资源配置（为避免 OOM 的堆冗余）是最大的可优化项之一。企业普遍反馈 Spark 内存利用率仅 30–50%。
2. **Rust 数据基础设施浪潮已被验证**：Arrow 统一列式内存标准成为事实标准；Polars（单机）与 DataFusion（查询层）证明了 Rust 内核相对 JVM 引擎数倍的性能/资源优势；商业侧 Photon（Databricks，C++）验证了"原生内核替换 JVM 执行层"路线的商业价值——但 Photon 闭源，开源世界尚无成熟的分布式完整对标品。
3. **存算分离成为默认架构**：对象存储 + 弹性计算是云上数据平台标配，新引擎应当原生为此设计而非事后适配（Spark 的 HDFS/本地性遗产）。
4. **K8s 之上自管集群仍有空间**：大量企业运行物理机/虚拟机集群，Spark Standalone 形态仍被广泛使用；不绑定 K8s 是务实选择，同时保留 Operator 上云路径。

### 2.2 Spark 痛点与解法映射

| 痛点 | 根因 | Flux 解法 | 对应需求 |
| --- | --- | --- | --- |
| 内存占用高、GC 停顿 | JVM 对象模型 + GC | Rust 无 GC、紧凑列式内存、精确记账 | FR-C04、NFR-PERF-3 |
| 作业/查询启动慢 | JVM 预热、类加载 | 常驻原生进程 + 池化线程 | NFR-PERF-5 |
| Shuffle 序列化开销 | 行式编码、跨语言边界 | 全链路 Arrow 列式批 + Flight 直传 | FR-C03、NFR-PERF-7 |
| 运维复杂 | JVM 参数体系 + 组件拼装 | 单二进制、配置收敛、doctor | FR-OP06 |
| 云上弹性摩擦 | 为 YARN 时代设计 | 无状态计算 + 对象存储优先 | ADR-004 |
| 排障链路长 | 日志分散 | trace_id 全链路贯穿 + OTel | FR-OP02/03 |

### 2.3 竞品对比

| 维度 | Spark 3.5 | Photon(Databricks) | Flink | Polars/DuckDB | Flux |
| --- | --- | --- | --- | --- | --- |
| 定位 | 通用批引擎王者 | 云上商业加速 | 流优先批可用 | 单机/嵌入式 | 开源分布式批引擎（长期批流一体） |
| 内核语言 | JVM/Catalyst | C++ 向量化 | JVM | Rust / C++ | Rust 自研向量化 |
| 内存效率 | 基线 | 强 | 中 | 极强 | 目标：内核原生效率 |
| 部署 | YARN/K8s/Standalone | 绑定平台 | 多形态 | pip/嵌入 | 自管集群 + 后续 Operator |
| SQL 兼容 | 高（事实标准） | =Spark | 中 | 中（各自方言） | ANSI 基线 + 差异显式文档 |
| 生态 | 极高 | 依附 Spark | 流领域高 | 单机场景 | 以 Parquet/Arrow/JDBC 开放标准切入 |
| 开源 | Apache-2.0 | 闭源核心 | Apache-2.0 | 开源 | 计划 Apache-2.0 |

**差异化结论**：不与 Comet/Velox（Spark 加速插件）竞争同一生态位，而是完整引擎 + 开放标准接口（SQL/Parquet/Arrow/JDBC）。用户迁移成本集中于 SQL 方言差异，以"差异显式文档 + 兼容模式开关（P2 评估）"消化。

### 2.4 市场风险

1. Spark 生态壁垒（UDF、BI 连接器、人才储备）——对策：JDBC/ODBC 前置调研、SQL 兼容说明、迁移指南。
2. 自研引擎成熟度信任门槛——对策：correctness-first 发布纪律、公开 TPC-H/TPC-DS 对比报告与复现脚本。
3. 重名/品牌（CNCF Flux）——对策：M0 定案项目名（Q4 开放问题）。

## 3. 目标用户与场景

### 3.1 用户画像（详细）

**P1 中小公司数据团队（3–10 人）**
- 环境：对象存储 + 几台虚机/物理机（8–32C），无专职大数据平台工程师，往往由后端兼任。
- 行为：白天 ad-hoc 查询 + 夜间 T+1 ETL；用 Airflow/Dolphin 调度。
- 诉求排序：部署简单（1 天内可用）> 成本（资源省一半）> SQL 标准 > 性能。
- 拒绝点：需要专职调优、组件多、文档晦涩。

**P2 中大型平台团队（有存量 Spark）**
- 环境：数十节点集群、多租户、有监控体系（Prometheus/Grafana/OTel）。
- 行为：寻求降本或替换试点；会跑基准、看指标、审架构白皮书。
- 诉求：性能对标报告（可复现）、可观测性接入现有栈、迁移工具、故障语义清晰。
- 拒绝点：正确性疑虑、生态缺口（Iceberg/UDF/BI）。

**P3 应用开发者（嵌入式）**
- 环境：Rust/后端服务，需在产品内做分析查询（日志分析、用户分群）。
- 诉求：单机模式 SDK 易用、资源占用小、无外部进程依赖。

### 3.2 Jobs-to-be-done

| JTBD | 陈述 | 当前方案 | Flux 方案 |
| --- | --- | --- | --- |
| JTBD-1 | "当我们需要把 S3 上的 Parquet 加工成数仓表时，我想提交 SQL 作业，以便第二天报表可用" | Spark on EMR/自建 | 集群提交 INSERT/CTAS |
| JTBD-2 | "当分析师需要即席查询明细时，我想秒级拿到结果" | Presto/Trino 或 Spark Thrift | 交互式查询（低启动开销） |

### 3.3 典型用户旅程（P1 用户首次采用）

1. 发现：技术博客/HN/GitHub trending——"Spark 替代品，Rust 写的，内存省一半"。
2. 评估：下载单二进制 → `flux sql --local` 对现有 Parquet 跑通 3 条查询 → 读兼容性文档确认 SQL 差异。
3. 试点：3 节点集群跑 T+1 ETL 双跑一周（与 Spark 结果对比脚本）。
4. 扩展：迁移全部 ETL → 接入调度器与监控 → （M4+）多租户。

**关键转化点**：第 2 步 10 分钟内跑通；第 3 步双跑对账通过。产品动作：快速开始文档 ≤ 10 分钟、双跑对账工具（`flux verify` 计划 P1 评估）。

## 5. 功能规格与范围划分

- 范围内：DAG 切分/调度/局部性/Shuffle 全策略/内存与 Spill/容错/取消/结果交付/推测执行(P2)。

### 5.5 Epic-5 工具与生态

- 范围内：CLI 全集/REST(P1)/Rust SDK/Go 客户端(P1)/JDBC·ODBC(P2)。
- 范围外：Python SDK 之上的建模工具、BI 前端。
- 依赖：Epic-1、Epic-4。

### 5.6 Epic-6 进阶计算

- 范围内：微批流/窗口/水位/exactly-once/checkpoint/CDC(P2)/线性与树模型/特征/ONNX/BSP 图算法。
- 范围外：在线学习服务化、GPU 训练、大规模图数据库语义。
- 依赖：Epic-3（执行内核）、Epic-2（状态与 sink）。

## 6. 产品目标与指标体系

### 6.1 北极星指标

**单位计算成本比** = （完成等量标准作业的机器成本 × 耗时）Flux ÷ 同项 Spark。

- 口径：TPC-H/TPC-DS 官方数据集；机器成本 = 按核时计价（元/核·时 × 核数 × 时长）；数据准备时间不计。
- 目标：M3 ≤ 0.6；长期（M4+）≤ 0.4。
- 复现：`benchmarks/` 提供双引擎同规格运行脚本与报告模板。

### 6.2 护栏指标（质量红线，任一恶化即冻结功能迭代）

| 指标 | 定义 | 阈值 |
| --- | --- | --- |
| 正确性缺陷 | P0/P1 已知语义错误数 | = 0（发布门禁） |
| 语义测试通过率 | 语义测试集通过比例 | ≥ 99.5%（M3 后 100%） |
| 性能回归 | 夜间 TPC-H 10GB 总耗时变化 | > +3% 报警、> +5% 阻断 |
| 内存泄漏 | 72h soak RSS 增幅 | < 5% |
| 稳定性 | 崩溃数（72h soak / 故障矩阵） | = 0 |

### 6.3 采纳指标（上线后按月跟踪）

| 指标 | 定义 | 目标（公开后 6 个月） |
| --- | --- | --- |
| 活跃集群数 | 30 天内有作业提交的集群 | ≥ 100 |
| 集群规模分布 | Worker 数 P50/P90 | P50 ≥ 3、P90 ≥ 20 |
| 日均作业数 | 全网作业提交量 | ≥ 10k |
| 交互查询占比 | < 30s 查询比例 | 反馈体验 |
| 社区指标 | star / PR / issue 首响 | 首响 < 48h |
| 迁移率 | 试点转全量比例 | ≥ 40% |

## 7. 路线图（详细）

> 周期为估算（团队 6–8 工程师当量），随排期校准；每个里程碑含进入条件/范围/退出标准/风险。

### M0 脚手架与预研（约 4 周）

- 范围：仓库结构（Rust workspace + Go module + proto + CI 全套）、本文档集评审定稿、三个技术 Spike（Spike-1 Parquet 扫描吞吐与谓词下推效果；Spike-2 Arrow IPC 编解码 + Flight 传输吞吐；Spike-3 tokio + 专用线程池混合执行模型验证）。
- 进入条件：文档评审通过、团队到位。
- 退出标准：CI 绿骨架；三份 Spike 报告含性能底数（支撑 NFR-PERF-7/8 可行性结论）；名字定案（Q4）。
- 风险：混合执行模型复杂度超预期 → 备选纯 tokio 方案（性能打折）。

### M1 单机引擎 MVP（约 10 周）

- 范围：flux-sql（词法/语法/语义）、flux-plan（逻辑计划+RBO+物理计划）、flux-exec（Scan/Filter/Project/HashAgg/HashJoin/Sort/TopN/Limit + 内存池 + Spill）、flux-storage（Parquet 读 + 对象存储 + 本地）、CLI 单机模式、CTAS/INSERT 单机。
- 退出标准：SRS §8.1 全部通过（AT-M1-01..05）。
- 关键依赖：Spike 结论。
- 风险：类型系统/NULL 语义工作量超估 → 函数目录按 P0 子集先行。

### M2 分布式批处理（约 10 周）

- 范围：flux-worker 进程化（Plan/Task 服务）、flux-shuffle 全策略、Go Master（apiserver/jobmanager/scheduler/workermanager/statestore/catalog）、CLI 集群模式、容错（重试/重算/黑名单）、指标/日志。
- 退出标准：SRS §8.2（AT-M2-01..06）。
- 风险：分布式正确性（乱序/重复）→ 以确定性测试框架（结果校验和）先行。

### M3 生产可用（约 12 周）

- 范围：CBO（统计/Join DP/SMJ）、分区表/分区裁剪、HDFS/JDBC/Kafka 批源、REST、Web UI、OTel、Master HA、TLS/Token、doctor、性能达标冲刺与公开报告。
- 退出标准：SRS §8.3 + NFR-PERF 全项。
- 风险：性能不达标 → 按"下推/并行度/内存布局"三个已识别优化杠杆逐项收敛，必要时调整目标并公示。

### M4 生态与多租户（约 10 周）

- 范围：Iceberg、ORC、UDF、多队列与 RBAC、审计、Grafana 看板市场版、JDBC 调研启动（ADR）。
- 退出标准：3 家早期用户试点接入（含至少 1 家生产）。

### M5 流处理（约 12 周）

- 范围：微批引擎、Kafka 源、事件时间/水位/窗口、exactly-once sink（Iceberg）、checkpoint/恢复、CDC。
- 退出标准：Kafka→Iceberg 混沌测试通过（SRS FR-S 验收）。
- 风险：与批内核的调度模型冲突 → M3 前完成"流式抽象预设计"评审（ADR-009）。

### M6 ML 与图（约 12 周）

- 范围：Flux ML（线性/树/特征/ONNX）、Flux Graph（BSP/算法库）。

### M7+ 云原生深化

- 范围：K8s Operator（CRD：FluxCluster/FluxWorkerPool）、自动扩缩容、动态资源分配。

### 排序原则

**正确性 → 分布式能力 → 性能 → 生态 → 新计算范式**。批+SQL 是地基，流/ML/图依次复用同一执行内核与调度体系（架构演进视图见概要设计第 13 章）。

## 8. 开源与商业化考虑

- **协议**：倾向 Apache-2.0（与 Spark/Flink 一致，最大化企业采用意愿）；定案前所有代码在本仓库（私有）开发。
- **时机**：M2 后公开（有可用的分布式能力 + 基准数据，避免"空仓库"印象）。
- **商业路径假设**（不承诺）：托管服务（Flux Cloud）与企业管理（RBAC/审计/SLA 支持）；核心引擎永久开源。此假设影响 M4 功能切分（RBAC 是否核心），需 M3 前定案。

## 9. GTM（Go-to-Market，M2 公开后启动）

1. **内容**：系列技术博客（架构、Rust 向量化内核、内存管理、Shuffle 设计）；TPC-H 对比报告（含复现脚本）是核心资产。
2. **渠道**：HN/Reddit（r/rust、r/dataengineering）、国内掘金/V2EX、Rust/数据社区会议分享。
3. **早期用户**：从试用反馈中筛选 3 家共建（P2 画像优先），提供白手套支持换取案例。
4. **反馈回路**：GitHub issue 模板分四类（bug/性能报告/生态缺口/文档），每两周公示 roadmap 变化。
