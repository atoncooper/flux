## 2. 通用工程纪律（双语言）

1. **trunk-based + 短特性分支**：分支命名 `<type>/<issue-id>-<slug>`（`feat/123-broadcast-join`、`fix/456-shuffle-leak`、`perf/789-agg-simd`）。
2. **提交信息 Conventional Commits**：`type(scope): subject`；scope 用 crate/包名（`feat(exec): grace hash join spill`）；type 限 `feat/fix/refactor/perf/test/docs/build/ci/chore`。
3. **PR 体量**：净变更 ≤ 400 行优先；更大改动拆为可独立验证的提交序列（每步可编译可测）。
4. **PR 必含**：动机（关联 issue/FR 编号）、测试证据（命令 + 输出摘要）、是否影响文档（架构维护文档第 9 节触发条件核对）、是否引入依赖（走轻量 ADR）。
5. **禁止合入**：lint 红灯、测试红灯、无 issue 号的 TODO、未处理的 `unwrap/panic`（Rust）或 `_ = err`（Go）。
6. **评审时限**：24h 内首响；意见分级 `must/should/nit`，仅 `must` 阻塞合入。
7. **提交前自检**（git hook 提供，命令见第 7.4 节）。

## 3. Rust 代码规范

### 3.1 格式与命名

- `cargo fmt` 强制（零个性化配置）；CI 校验。
- 命名：类型/trait `UpperCamelCase`；函数/变量/字段 `snake_case`；常量 `SCREAMING_SNAKE`；crate 名 `flux-<module>`；缩写词整体小写（`HttpClient` 而非 `HTTPClient`、`task_id` 而非 `taskID`）。

```rust
// ✅
struct HttpClient { retry_policy: RetryPolicy }
const MAX_BATCH_ROWS: usize = 65_536;
fn fetch_task_by_id(task_id: &TaskId) -> Result<Task> { ... }

// ❌
struct HTTPClient { ... }           // 缩写词大写
const maxBatchRows = 65536;          // 非常量命名风格
fn fetchTaskByID(taskID) { ... }     // 驼峰 + 缩写
```

### 3.2 错误处理（数据面最重要的纪律）

**规则**：跨 crate 公共 API 禁止 `unwrap/expect/panic!`；用 `Result<T, FluxError>`。CI 对公共 crate 开 `clippy::unwrap_used`、`clippy::expect_used` 为 deny。`unwrap` 仅允许：单元测试、进程启动早期、`// INVARIANT:` 证明性注释。

```rust
// ❌ 公共 API 中 unwrap
pub fn schema(&self) -> &SchemaRef {
    self.schemas.get(0).unwrap()
}

// ✅ 启动期（配置装载，失败即退出是合理语义）
let cfg = WorkerConfig::load().unwrap_or_else(|e| {
    eprintln!("invalid config: {e}"); std::process::exit(2);
});

// ✅ 证明性不变量（须解释为什么不可能失败）
let n = batch.num_columns();
let schema = self.schemas.first()
    .expect("INVARIANT: constructor rejects empty schema list");
```

- 错误信息面向用户：含上下文（表/列/分区），不含堆栈（堆栈进 tracing）：

```rust
// ❌
return Err(FluxError::internal("failed"));

// ✅
return Err(FluxError::new(ErrorCode::DataScanFailed)
    .with_context(format!("scanning {} files under {}", files.len(), self.location))
    .with_source(e));
```

- panic 边界：Task 主体 `catch_unwind`（详细设计 6.5）；新线程必装 panic hook；库代码不得以 panic 作为控制流。

### 3.3 异步与并发

**规则回顾**：计算线程与 IO runtime 分离（AR-7 的执行面）；跨界数据走**有界** channel；async 上下文禁阻塞调用；锁跨 await 需评审确认。

```rust
// ❌ 计算线程内同步 IO（热路径阻塞）
fn execute(&self, ctx: &TaskContext) -> Result<SendableRecordBatchStream> {
    let data = std::fs::read(&self.path)?;   // 同步文件读
    ...
}

// ✅ 经有界 channel 由 IO runtime 预取，计算侧纯内存
let (tx, rx) = tokio::sync::mpsc::channel::<RecordBatch>(4);   // 容量=预取批数
let io = self.storage.clone();
tokio::spawn(async move {
    let mut stream = io.scan(prefetch_spec).await?;
    while let Some(batch) = stream.next().await {
        if tx.send(batch?).await.is_err() { break; }   // 下游取消 → 停止预取
    }
});

// ❌ unbounded channel（背压缺失，内存不可控）
tokio::sync::mpsc::unbounded_channel();

// ❌ async 上下文持有 std::sync::Mutex 跨 await
let guard = self.cache.lock().unwrap();
let data = fetch_remote().await;    // guard 跨 await：死锁/饿死风险

// ✅ 读多写少用不可变快照（arc-swap 风格）
let snapshot = self.snapshot.load();   // Arc<ClusterView>，无锁读
```

- goroutine/task 生命周期可归属：每个 spawn 的任务有明确取消路径（channel 关闭/cancel 令牌），禁止"发射后不管"。
- `Send + Sync` 只加在真正需要的边界；避免为绕生命周期 `Arc<Mutex<...>>` 泛滥。

### 3.4 性能敏感区规范

```rust
// ❌ 逐行闭包虚调用 + 每行堆分配
for i in 0..batch.num_rows() {
    let s = format!("{}", col.value(i));      // 热路径 String 分配
    if pred(&s) { out.push(i); }
}

// ✅ 列式批处理 + 预分配
let mask = self.predicate.eval(&batch)?;       // 列式求值 → BooleanArray
let filtered = arrow::compute::filter_record_batch(&batch, &mask)?;

// ❌ 热路径日志无条件构造
log::debug!("batch {:?}", batch);

// ✅ 级别守卫 + 结构化字段
tracing::debug!(rows = batch.num_rows(), "batch received");
```

- 热路径避免每批分配：`Vec` 预估容量复用；arena（bumpalo 等）引入须登记。
- `unsafe` 规范（AR-9）：

```rust
// ✅ unsafe 三要素：白名单 crate、SAFETY 注释、对应测试
// SAFETY: `ptr` 来自 Arrow FFI 导出的 array，生命周期由 `owner`（FFI ArrayRef）
// 保证；本函数内不释放、不越界（len 由 FFI header 携带并已校验）。
unsafe fn take_ffi_array(ptr: *const Ffi_ArrowArray) -> ArrayRef { ... }

#[test]
fn ffi_roundtrip_preserves_data() { ... }       // 对应测试必须有
```

- SIMD：优先 arrow compute（已 SIMD 化）；手写 intrinsics 须附 criterion 数据证明收益 ≥ 15%。

### 3.5 模块组织

- 单文件 ≤ 800 行、单函数 ≤ 80 行为软上限（评审可例外但需说明）。
- 可见性最小化：默认私有；跨 crate 公共类型必须有 rustdoc（含 `# Errors`；`# Panics` 段出现即需按 3.2 证明）。
- 测试与实现同 crate（`#[cfg(test)]`）+ `tests/` 集成测试。

### 3.6 Rust 惯例速查

| 场景 | 规范 |
| --- | --- |
| 入参 | 借用优先 `&T`/`&[T]`；所有权转移才 `T`；返回大对象共享用 `Arc<T>` |
| trait 对象 vs 泛型 | 数据面热路径泛型（静态分发）；插件注册用 `dyn` |
| `Clone` | 计划/配置可 Clone；执行期批数据禁止整批 Clone（传 `Arc`） |
| 时间 | 内部 UTC + 显式 TimeUnit；展示层才做时区 |
| 依赖版本 | 一律在 workspace 根 `[workspace.dependencies]` 集中声明 |

## 4. Go 代码规范

### 4.1 格式与命名

- `gofmt`/`gci`（import 分组：标准库 / 第三方 / 本项目）强制；包名全小写单数；导出标识符注释以标识符名开头；接口定义在消费侧（AR-11）。

```go
// ✅ 消费侧接口（jobmanager 只依赖它需要的能力）
type taskDispatcher interface {
    LaunchTask(ctx context.Context, w WorkerId, t TaskSpec) error
    CancelTask(ctx context.Context, w WorkerId, task TaskRef) error
}

// ❌ 实现侧大而全接口 + I 前缀
type IScheduler interface { ScheduleAll(...) /* 12 个方法 */ }
```

### 4.2 错误处理

```go
// ❌ 吞错误
_, _ = w.conn.Close()

// ✅
if err := w.conn.Close(); err != nil {
    w.log.Warn("close worker conn", "err", err)
}

// ❌ 字符串匹配错误
if err != nil && strings.Contains(err.Error(), "timeout") { ... }

// ✅ 错误码判定（proto 枚举）
if fluxerr.Code(err) == fluxv1.ErrorCode_QUEUE_TIMEOUT { ... }

// ✅ wrap 一律 %w（保留链）
return fmt.Errorf("dispatch task %s to %s: %w", t.ID, w.ID, err)

// ❌ 循环内 defer
for _, f := range files {
    fd, _ := os.Open(f)
    defer fd.Close()            // 循环结束前不释放
}

// ✅ 提取函数
for _, f := range files {
    if err := processFile(ctx, f); err != nil { return err }
}
```

- `panic` 仅限启动期不可恢复；gRPC/HTTP handler 顶层 recover 中间件统一兜底（转 500/内部错误码）。

### 4.3 并发规范

```go
// ✅ goroutine 有 owner 与退出路径
func (m *WorkerManager) Run(ctx context.Context) error {
    g, ctx := errgroup.WithContext(ctx)
    g.Go(func() error { return m.heartbeatLoop(ctx) })   // 随 ctx 退出
    return g.Wait()
}

// ❌ 发射后不管
go m.syncCatalog()               // 无取消路径、错误无人消费

// ✅ 长等待必含 Done 分支
select {
case ev := <-m.events:
    m.handle(ev)
case <-ctx.Done():
    return ctx.Err()
}

// ❌ Sleep 轮询
for { time.Sleep(time.Second); m.checkState() }

// ✅ 事件驱动（或注释说明的指数退避）
m.watcher.Subscribe(m.onWorkerChange)
```

- JobManager 状态写路径唯一（AR-12）：其他模块经 `Submit/Cancel/Events()` 交互，不改状态字段。
- 集群视图读侧禁止持锁遍历（AR-13）：用 COW 快照（`atomic.Pointer[ClusterView]`）。

### 4.4 API 与包组织

- gRPC handler 是薄层：校验 → 调内部模块 → 映射错误码；业务逻辑禁止写在 handler。
- 配置集中 `internal/config`（带 TOML/godoc 标签）；`os.Getenv` 仅 main 装配层。
- 依赖注入：main 显式构造，不引入 wire/dig 类框架。

### 4.5 Go 惯例速查

| 场景 | 规范 |
| --- | --- |
| 切片容量 | 已知大小 `make([]T, 0, n)`；不对外暴露内部切片（copy 或注释说明） |
| 时间 | `time.Time` UTC；存储/协议用 Unix 毫秒 int64（与 Rust 对齐） |
| 日志 | `slog`；字段 snake_case：`job_id/stage_id/task_id/trace_id/worker_id` |
| context | 一切 IO 第一参数 `ctx`；`context.Background()` 仅限 main/测试 |
| 表驱动测试 | 子测试名描述行为（`"returns shuffle lost when bucket missing"`） |

## 5. 测试规范

### 5.1 分层与门禁

| 层级 | 要求 | 门禁 |
| --- | --- | --- |
| 单元 | 每个导出函数覆盖正常/边界/错误三态；表驱动 | 每 PR；覆盖率见 NFR-MAINT |
| 语义 | yml 用例（query + fixture + 期望结果），NULL/溢出/时区/精度专集 | 每 PR |
| 计划 golden | SQL → 三级计划快照对比 | 每 PR |
| 集成 | 每个 FR-x ≥ 1 条端到端用例，标签对应 FR 编号 | 冒烟每 PR / 全量每夜 |
| 基准 | 新增/修改算子必附 criterion 基准；对照预算表 | 每 PR |
| 故障注入 | 容错路径（FR-C05）必须有 chaos 用例 | 每夜 |

### 5.2 测试命名与数据

- Rust：`#[test] fn <被测>_<场景>_<预期>`：

```rust
#[test]
fn hash_partition_null_key_goes_to_bucket_zero() { ... }

#[test]
fn cast_varchar_overflow_returns_error_3006() { ... }
```

- Go：表驱动 + 行为命名：

```go
func TestSchedulePrefersLocalShuffle(t *testing.T) {
    tests := []struct{ name string; view ClusterView; task StageTask; want WorkerId }{
        {name: "map output on same worker scores higher", view: localView, task: reduceTask, want: w1},
        {name: "blacklisted worker never selected", view: blacklistView, task: reduceTask, want: w2},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) { ... })
    }
}
```

- fixture 放 `testdata/`；> 1MB 的数据走生成脚本（`scripts/`），禁止提交大二进制。
- 语义测试 yml 结构：

```yaml
id: ST-0142
fr: [FR-B02, FR-B06]
sql: SELECT a.id, b.amount FROM a LEFT JOIN b ON a.id = b.id
fixtures:
  a: {schema: "id INT64, k UTF8", rows: [[1, 'x'], [2, null]]}
  b: {schema: "id INT64, amount FLOAT64", rows: [[1, 1.5]]}
expect:
  columns: [id, amount]
  rows: [[1, 1.5], [2, null]]
  order_insensitive: true
```

### 5.3 覆盖率与产物

- 门槛：`flux-exec`/`flux-plan`/`scheduler` ≥ 80%，整体 ≥ 70%（CI 上传报告 + PR 评论）。
- 双端复跑：语义用例在单机与本地集群两路径各跑一遍（TD-003 合一前为必须项）。

## 6. 文档与注释规范

1. **注释写"为什么"，不写"是什么"**：

```rust
// ❌ 遍历批数据
for b in batches { ... }

// ✅ 说明约束/来源
// Map 端桶必须按 reduce 桶切片写入：下游 Flight 拉取以桶为最小单位，
// 跨桶合并会导致重算粒度放大（见 docs/04 §7.2）。
```

2. Rust 公共 API 必须有 rustdoc（`# Errors` 必填；出现 `# Panics` 需按 3.2 提供证明性注释）。
3. Go 导出标识符必须有 godoc 注释（以标识符名开头）。
4. 语言约定：docs/ 中文；代码注释、提交信息、issue 英文（CLAUDE.md 全局约定）。
5. 计划/算法细节落在详细设计文档，代码注释只留指向（`// see docs/04 §6.3`），避免双份漂移。

## 7. 提交流程与模板

### 7.1 PR 模板（`.github/pull_request_template.md`）

```markdown
## 动机
<!-- 关联 issue / FR 编号；为什么做 -->

## 方案概要
<!-- 关键设计决策；如命中 ADR 触发条件（架构维护文档 §3.1）请链接 ADR -->

## 测试证据
<!-- 运行的命令与结果摘要：cargo test/go test、语义用例数、基准数据 -->

## 影响核对
- [ ] 影响 proto 契约（buf breaking 通过）
- [ ] 引入新依赖（已附轻量 ADR：动机/替代/许可/维护状态）
- [ ] 影响文档（SRS/PRD/HLD/LLD/维护/规范，列出章节）
- [ ] 影响性能（附 criterion 数据）
- [ ] 新增 TODO（均已关联 issue 号）
```

### 7.2 评审检查清单（评审人按序过）

```text
[ ] 正确性：边界（空集/NULL/溢出）是否有测试覆盖
[ ] 架构：是否触碰 AR-1..13（语言边界/依赖方向/热路径纪律）
[ ] 错误处理：错误码正确、上下文完整、无 unwrap/_ = err
[ ] 并发：goroutine/task 生命周期、锁范围、channel 有界
[ ] 性能：热路径无行级分配/同步 IO；基准数据支撑
[ ] 测试：新逻辑有对应用例；语义/golden 更新
[ ] 文档：命中触发条件已更新（含本文档第 9 章触发点）
[ ] 可观测：新增路径有日志/指标（按需）
```

### 7.3 提交信息示例

```text
feat(shuffle): bucket-level ready table reporting

Report per-bucket output (bytes/rows/checksum) in TaskEvent so the
reduce side can fetch via Flight without a central manifest lookup.

Closes #123
```

```text
fix(exec): spill run leak on cancelled sort tasks

Task cancellation left sort runs on disk because cleanup only ran on
the success path; move deletion into Drop of the task scope.

Closes #456
```

### 7.4 提交前自检（git hook）

```bash

go vet ./... && golangci-lint run
cargo test --workspace && go test ./... -race
buf lint && make proto-check
```

## 8. 发布清单

发布负责人按[架构维护文档 5.3 节 runbook](05-架构与代码维护文档.md#53-分支与发布流程) 执行（八步：CI 全绿 → 兼容矩阵复核 → 性能预算核对 → 漏洞扫描 → CHANGELOG → tag → 产物冒烟 → 公告）。发布附加项：`cargo audit`/`govulncheck` 高危 = 0；Grafana 看板与 sql-compat.md 随版本同步。

## 9. 新人上手路径

### 30/60/90 天

**第 1 周（环境与心智模型）**：
1. 读 CLAUDE.md → 本文档第 1–2 节 → 概要设计第 3、4 章（架构与 ADR）。
2. 跑通 `make dev-cluster` + `flux sql -e "SELECT 1"`；用 `flux doctor` 巡检本地集群。
3. 完成一个 `good-first-issue`（SQL 函数补齐/错误信息完善类）。

**30 天（可独立交付）**：

## 10. FAQ

**Q1：为什么 Go 和 Rust 不用 FFI 直调，性能不是更好吗？**
边界即团队与故障域（ADR-001）。FFI 把两个运行时的 GC/内存/线程模型耦合在一起，失去独立演进能力。同机高性能已由共享内存 IPC 承担（ADR-011）：控制流 shm 环形缓冲 + 数据流 Arrow 零拷贝区域，无 TCP 回环协议栈成本；网络仅跨机。跨语言调用栈仍被完全禁止（AR-2）。

**Q1b：shm IPC（flux-shmipc / internal/shmipc）开发有什么特别纪律？**
这是唯一允许操作共享内存的模块，额外规则：热路径禁止跨进程锁（锁仅限建连与异常恢复）；data 区只放自描述块（块头含长度/校验），**禁止放置指针语义数据**（对端崩溃后按布局版本号整体作废，指针会悬空）；新增消息类型必须走 proto（AR-1），禁止在 shm 上私加绕过 proto 的编码；两侧实现共享同一套往返一致性测试（与 gRPC 路径同用例）。

**Q2：为什么允许用 arrow-rs 却不用 DataFusion？（常被挑战）**
arrow-rs 是**格式标准库**（类型/IPC/Parquet 编解码），不含计划与执行；DataFusion 是执行框架，引入它等于放弃"自研内核"这一核心决策（ADR-002）。白名单由 AR 守护。

**Q3：热路径的判定标准是什么？**
逐批执行的算子与表达式代码（`execute()` 调用图可达）。简单判据：该函数是否会出现在 `flux_worker_task_duration_seconds{operator}` 指标的栈里。

**Q4：为什么公共 API 禁 unwrap，测试可以？**
测试失败即信号本身；生产 unwrap 在数据面等价于拒绝服务的 panic。启动早期（配置装载）是唯一例外：失败即退出是正确语义。

**Q5：语义测试为什么双端复跑？**
单机与集群共享内核但序列化路径不同（TD-003）；在合一前，双端复跑是防契约漂移的最低成本手段。

**Q6：提交信息为什么全英文？**
可检索性与工具链（Conventional Commits 解析、changelog 自动生成）依赖统一语言；文档语言与代码语言分离是 CLAUDE.md 既定约定。
